## Current decision

**Status: code-level MVP candidate; Phase 0–4 acceptance is not complete.** The Core and Runtime
provide a substantial, durable graph engine. The bridge has the main admission, outbox, tool,
projection, and scope paths. The development host reports a ready PolyForge plugin, but it is a
separately staged older path; the current checkout has not been installed or exercised end-to-end
on that host. Do not call the current build pilot-ready until that host acceptance is completed.

Do not use this status as authorization for production cutover, unattended deployment, or work that
requires workspace isolation. The current deployment uses the explicitly pilot-only `direct`
Runtime transport and metadata-only workspace handling; the live host does not expose a verified
privileged-action authorization route or a confirmed worker-stop API to this plugin. Its OpenAPI
does declare a heartbeat-run cancellation route, but the plugin SDK does not expose that
run-scoped operation under the capabilities currently granted to PolyForge.

## Functional boundary today

The intended safe path is Root Issue → admitted GraphRun → ready node → child Issue → Paperclip
assignment/wakeup → agent tool calls → evidence → Core transition → status projection. The Core does
not spawn agents, and the bridge does not mark nodes passed from an Issue status or agent exit.

The matcher can select/reject workers only when explicit engineering bindings already exist. This
checkout has no production workflow to create or revoke those grants; test helpers and the internal
`seedBindings` method are not an operator interface. Consequently, a fresh installation cannot
authorize real agents for graph work through a supported product workflow yet.

For a downstream graph that declares prerequisite facts, the issue intent names the completed
source Run, not a claimed result or a user-supplied digest. For example, a Design start supplies
`requiredFactSources: { "requirement_acceptance": { "sourceRunId": "<completed Requirement run>" } }`.
The Core resolves that reference against its own same-project run and Gate records; arbitrary
Issue-body `requiredFacts` are not forwarded by the plugin. Only supported fact names exported by
exactly one passed Gate can be handed off this way.

The following modes must stay disabled or blocked until their Phase 0–4 gates have evidence:

- deployment, release, or any other privileged external effect;
- workspace flows that depend on the bridge enforcing filesystem or parallel-writer isolation;
- adoption of a replacement worker when the previous worker is not confirmed stopped;
- a direct Runtime transport in a production deployment;
- Hermes modes whose gateway, context, cancellation, and recovery behavior have not been verified.
- issue-attachment evidence uploads while `issue.attachments.read` remains unrequested; use scoped issue documents or inline content.
